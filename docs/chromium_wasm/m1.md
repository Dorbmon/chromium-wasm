# M1: Chromium runtime foundation

M1 establishes the Base, Rust, process-local shared-memory, and in-process Mojo
foundation required before V8 or Content work. This document begins with the
M1.0 pinned-source inventory; later phases append verified implementation and
runtime results.

The source basis is Chromium `24b04c927b23c39cf9c5227cc8dc6f64a744c8e9`
(`150.0.7871.181`) plus the M0 port commit
`831de29bfdf212c26f61ffbd828e5377732fb2bc`, tagged
`wasm-m0-primary-toolchain`. The machine-readable inventory is
[`tools/wasm/m1_inventory.json`](../../tools/wasm/m1_inventory.json), and the
versioned product ledger is
[`docs/chromium_wasm/porting_ledger.md`](porting_ledger.md).

## M1.0 baseline

Before changing runtime source selection, the M0 gate was rerun from the tagged
workspace:

```bash
git status --short
git log --oneline -12
git show --no-patch --decorate wasm-m0-primary-toolchain
git tag --points-at HEAD
git merge-base --is-ancestor wasm-m0-primary-toolchain HEAD

python3 tools/wasm/bootstrap.py --verify-only

export PATH="$PWD/buildtools/linux64:$PWD/third_party/depot_tools:$PATH"
export XDG_CONFIG_HOME="$PWD/out/wasm-xdg"

gn gen out/wasm
autoninja -C out/wasm hello_wasm
python3 -m unittest discover -s tools/wasm/tests -p 'test_*.py' -v
python3 tools/wasm/run_node_smoke.py out/wasm/hello_wasm.js
python3 tools/wasm/run_browser_smoke.py --case hello
unshare --user --map-root-user --net -- \
  python3 tools/wasm/bootstrap.py --verify-only
```

All commands passed. GN generated 29 targets from 63 files. The unit suite ran
13 tests. Node ended with `CHROMIUM_WASM_M0_NODE:PASS`. Sandboxed Chrome ended
with `CHROMIUM_WASM_M0_BROWSER:PASS`, reported cross-origin isolation and
`SharedArrayBuffer`, and advanced the JavaScript heartbeat by 26 ticks during
the C++ runtime interval. Offline verification passed in a network namespace.

The first expected inventory probe does not resolve:

```text
$ gn desc out/wasm //base:base deps --tree
The input //base:base matches no targets, configs or files.
```

This is not a compiler failure. The M0 root graph intentionally reaches only
`//wasm:hello_wasm`, and `base/BUILD.gn` still asserts that Base must not build
for Wasm.

## Root-cause inventory

### Source selection

The opt-in root group has no Base, Rust, or Mojo target. Base's platform source
lists cover POSIX, Linux, Apple, Android, Fuchsia, and Windows, but not Wasm.
M1 will add only focused smoke targets and deliberate Wasm source lists. It
will not set Wasm to Linux or POSIX.

The first M1.1 gate is:

```text
//tools/wasm:m1_base_smoke
```

Its first behavior slice is wall time, monotonic time, and secure entropy. The
exact initial implementation paths are:

```text
BUILD.gn
base/BUILD.gn
base/rand_util.h
base/time/time.h
base/time/time_wasm.cc
base/rand_util_wasm.cc
tools/wasm/BUILD.gn
tools/wasm/m1_base_smoke.cc
tools/wasm/toolchain_manifest.json
```

`base/BUILD.gn` will expose a narrowly gated
`//base:base_wasm_primitives` target only when both
`enable_chromium_wasm_port` and `is_wasm` are true. This avoids pretending that
the full `//base:base` graph is ready and avoids loading unrelated V8, Content,
or Chrome work.

### Base platform ABI

The C++ `BUILDFLAG(IS_WASM)` and `ARCH_CPU_WASM32` definitions already exist,
while `IS_POSIX` is deliberately false. Several Base ABI headers have no Wasm
type branch: platform thread IDs and handles, pthread lock/CV storage, file
descriptors, narrow paths and stat metadata, and process handles.

Targeted Wasm branches are required. Emscripten pthread mutexes, condition
variables, keys, and virtual filesystem descriptors may be reused only through
explicit source selection and focused behavior tests.

### Base primitives

- Add `base/time/time_wasm.cc` for wall and monotonic clocks. Monotonic elapsed
  time must not use a wall-clock source. Add a distinct Emscripten clock
  identity to `base/time/time.h`; do not label it as Linux monotonic time.
- Add `base/rand_util_wasm.cc` around Emscripten `getentropy`, whose pinned
  runtime path is backed by host cryptographic randomness. Failure must remain
  failure. The public header's nonallocating generator currently includes an
  unhydrated BoringSSL header; its Wasm branch will preserve the API by calling
  the nonallocating Wasm provider directly.
- Add `base/threading/platform_thread_wasm.cc`; do not inherit POSIX niceness or
  native priority behavior. IDs must be stable and names are explicitly
  best-effort diagnostics. pthread lock, condition-variable, waitable-event,
  and TLS implementations are candidates for explicit reuse.
- Add `base/base_paths_wasm.cc` for paths that actually exist in the
  Emscripten VFS. POSIX XDG and native executable paths are not valid defaults.
- Reuse POSIX-shaped file operations only after verifying their MEMFS
  semantics for create, read/write, truncate, flush, rename, metadata, errors,
  enumeration, and close.
- Add one stable process-local identity and accurate system information.
  Process launch, enumeration, dynamic libraries, and native executable memory
  remain explicitly unsupported.

The focused subset initially disables PartitionAlloc and the allocator shim.
Those source graphs have their own missing Wasm platform selections and are not
needed to prove the M1 Base API behavior.

### Task runtime

The pinned `MessagePumpDefault` already waits through `WaitableEvent`, wakes on
cross-thread `ScheduleWork`, handles immediate and delayed work, and is selected
by `MessagePump::Create(DEFAULT)`. It has no file-descriptor dependency.

M1.2 therefore evaluates the generic pump first on the application pthread.
`//tools/wasm:m1_task_smoke` must prove delayed ordering, cross-thread wake,
nested loops, quit during sleep, bounded idle wake counts, and clean shutdown
while the browser heartbeat continues. A dedicated pump will be added only if
this behavioral gate exposes a real gap.

### Rust

The M0 manifest and Chromium `DEPS` pin:

```text
rust-toolchain-4c4205163abcbd08948b3efab796c543ba1ea687-5-llvmorg-23-init-10931-g20b6ec66.tar.xz
sha256 5b4f776f6f308ac5e3f1df35cff546107d7d4843b5414294e74986f2e4dd3196
```

M0 only verifies that these values occur in `DEPS`; the current checkout has no
installed `third_party/rust-toolchain`. Read-only characterization of an
installed compiler from the identical pinned package reported Rust
`1.96.0-nightly`, commit `4c4205163abc...`, and LLVM `23.0.0`. Its target list
contains `wasm32-unknown-emscripten`, but its packaged rustlib has no standard
library for that target. The archive bytes were not retained, so M1.0 does not
claim an independent archive-hash verification.

M1.3 must first extend bootstrap to install and hash the exact archive. The
target stdlib will then be built reproducibly from its bundled `rustc-src`
through `build/rust/std`, using `panic=abort` and the same atomics,
bulk-memory, mutable-globals, and pthread contract as C++.

GN currently has four independent gates: Chromium Rust support is
`!is_wasm`, there is no Emscripten triple mapping, `rust_target_arch` has no
wasm32 branch, and `known-target-triples.txt` omits the target. The existing
Chromium rustc wrapper and Emscripten-owned final C++ link are the intended
archive path. Cross-revision LLVM bitcode and ThinLTO remain disabled.
The Chromium prelude is also disabled by the M0 Rust configuration and will be
enabled only after the target stdlib can compile.

The stable targets are:

```text
//tools/wasm:m1_rust_smoke
//tools/wasm:m1_rust_panic_negative
```

The positive smoke will use Chromium's existing CXX interoperability model to
prove C++ to Rust and Rust to C++, plus `Vec`, `String`, heap allocation,
integer widths, atomics, and pthread spawn/join. The negative target must abort
and must never be reported as success.

### Process-local shared memory

The current fallback in `platform_shared_memory_handle.h` names a POSIX
`FDPair` even though that type is not declared for Wasm. Wasm therefore gets a
separate process-local implementation; it does not reuse a Unix descriptor,
`mmap`, or a numeric value which could be mistaken for either.

#### Handle and identity

The platform handle is an opaque capability value containing a monotonically
allocated region ID, a generation, and rights. The scoped handle owns one
registry reference and is move-only. It never treats a storage address as the
transfer identity. The registry keeps the authoritative size, mode, and
128-bit `UnguessableToken` GUID; adoption checks all supplied metadata against
that record. A missing ID, stale generation, corrupted metadata, or rights
mismatch yields an invalid region or `TakeOrFail()` error instead of silently
creating an alias.

Writable ownership remains unique: it can be moved, converted to read-only, or
converted to unsafe, but not duplicated. Read-only and unsafe capabilities may
be duplicated when their typed Base APIs allow it. Conversion changes the
authoritative rights atomically and cannot promote a read-only capability back
to writable.

#### Storage and mapping lifetime

A locked, process-local registry owns each allocation independently of its
container. Storage is zero-initialized and aligned to
`SysInfo::VMAllocationGranularity()` (64 KiB for wasm32), which is stronger
than Base's public 32-byte minimum and lets partial mappings round-trip through
Base's align-down unmap path. The lock protects region creation, handle and
mapping reference counts, mode transitions, and lookup; callers synchronize
the bytes themselves through normal C++ atomics, locks, or other agreed
protocols.

Mapping validates the region ID, generation, current rights, offset, size, and
overflow before returning a span into the owning allocation. Every successful
map retains a mapping reference. Unmap decrements the matching
`{address, size}` count, so identical process-local mappings are supported.
Storage is freed only after both the final handle and final mapping are gone;
moving or destroying a handle therefore cannot invalidate an active mapping.
Zero-sized and out-of-range maps fail, and executable mappings are unsupported.

WebAssembly memory growth preserves intra-module pointer offsets, so C++
mappings remain valid. Growth can replace JavaScript's `ArrayBuffer` and typed
array views, however, so any later host bridge must reacquire a view after
growth; M1 exposes no persistent host view.

#### Protection boundary and limitations

Read-only enforcement is logical, not hardware-backed. The registry rejects a
writable map request made with read-only rights, and the public typed API
returns only `ReadOnlySharedMemoryMapping`. WebAssembly linear memory cannot
page-protect the same bytes from deliberately unsafe code already inside the
module, and M1 does not claim that guarantee. Existing writable mappings made
before demotion retain the lifetime and access promised by the pinned Base
API.

The focused M1 graph has tracing disabled. Native `mmap` normally provides a
distinct virtual address for each mapping, while this backend aliases the same
allocation; shared-memory usage tracking must therefore be explicitly omitted
for Wasm until it supports reference-counted duplicate addresses. The registry
still performs real ownership accounting and never fabricates distinct
mappings by copying storage.

### Mojo

This pin uses ipcz outside ChromeOS; enabling legacy Mojo would be the wrong
port. A local message pipe creates a pair of local ipcz routers, and attached
API objects move directly in a parcel without platform-handle serialization.

Compilation still encounters native assumptions in `mojo::PlatformHandle`,
platform channels, and ipcz shared-buffer fallbacks. Wasm will get only the
process-local shared-region capability needed by ipcz. Platform channels and
native C handle wrapping return explicit unsupported results. Remote
serialization is rejected.

The stable gate is:

```text
//tools/wasm:m1_mojo_smoke
```

It will depend on `//mojo/core/embedder:embedder` and
`//mojo/public/c/system:system`, initialize one node, and use the C API to
create/map/write/attach/send/receive/extract/map/verify/close a shared buffer
through one local message pipe. It will not create an invitation, transport,
platform channel, or second node.

## M1.0 result

The dependency and source-selection inventory is complete against the pinned
checkout. Runtime behavior is unchanged in this phase. M1.1 begins with the
focused time and secure-entropy slice named above; no V8, Blink, Content,
Ozone, networking, persistence, media, or Chrome UI work is in scope.
