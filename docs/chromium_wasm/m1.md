# M1: Chromium runtime foundation

M1 establishes the Base, Rust, process-local shared-memory, and in-process Mojo
foundation required before V8 or Content work. The inventory sections below
preserve the M1.0 state as historical pre-implementation evidence; the final
implementation, commands, measurements, and limitations are recorded after
that inventory.

The source basis is Chromium `24b04c927b23c39cf9c5227cc8dc6f64a744c8e9`
(`150.0.7871.181`) plus the M0 port commit
`831de29bfdf212c26f61ffbd828e5377732fb2bc`, tagged
`wasm-m0-primary-toolchain`. The machine-readable inventory is
[`tools/wasm/m1_inventory.json`](../../tools/wasm/m1_inventory.json), and the
versioned product ledger is
[`docs/chromium_wasm/porting_ledger.md`](porting_ledger.md).

## Root-cause inventory

### Source selection

The opt-in root group has no Base, Rust, or Mojo target. Base's platform source
lists cover POSIX, Linux, Apple, Android, Fuchsia, and Windows, but not Wasm.
M1 will add only focused smoke targets and deliberate Wasm source lists. It
will not set Wasm to Linux or POSIX.

The first M1.1 gate is:

```text
//tools/wasm:m1_base_smoke
```

Its first behavior slice is wall time, monotonic time, and secure entropy. The
exact initial implementation paths are:

```text
BUILD.gn
base/BUILD.gn
base/rand_util.h
base/time/time.h
base/time/time_wasm.cc
base/rand_util_wasm.cc
tools/wasm/BUILD.gn
tools/wasm/m1_base_smoke.cc
tools/wasm/toolchain_manifest.json
```

`base/BUILD.gn` will expose a narrowly gated
`//base:base_wasm_primitives` target only when both
`enable_chromium_wasm_port` and `is_wasm` are true. This avoids pretending that
the full `//base:base` graph is ready and avoids loading unrelated V8, Content,
or Chrome work.

### Base platform ABI

The C++ `BUILDFLAG(IS_WASM)` and `ARCH_CPU_WASM32` definitions already exist,
while `IS_POSIX` is deliberately false. Several Base ABI headers have no Wasm
type branch: platform thread IDs and handles, pthread lock/CV storage, file
descriptors, narrow paths and stat metadata, and process handles.

Targeted Wasm branches are required. Emscripten pthread mutexes, condition
variables, keys, and virtual filesystem descriptors may be reused only through
explicit source selection and focused behavior tests.

### Base primitives

- Add `base/time/time_wasm.cc` for wall and monotonic clocks. Monotonic elapsed
  time must not use a wall-clock source. Add a distinct Emscripten clock
  identity to `base/time/time.h`; do not label it as Linux monotonic time.
- Add `base/rand_util_wasm.cc` around Emscripten `getentropy`, whose pinned
  runtime path is backed by host cryptographic randomness. Failure must remain
  failure. The public header's nonallocating generator currently includes an
  unhydrated BoringSSL header; its Wasm branch will preserve the API by calling
  the nonallocating Wasm provider directly.
- Add `base/threading/platform_thread_wasm.cc`; do not inherit POSIX niceness or
  native priority behavior. IDs must be stable and names are explicitly
  best-effort diagnostics. pthread lock, condition-variable, waitable-event,
  and TLS implementations are candidates for explicit reuse.
- Add `base/base_paths_wasm.cc` for paths that actually exist in the
  Emscripten VFS. POSIX XDG and native executable paths are not valid defaults.
- Reuse POSIX-shaped file operations only after verifying their MEMFS
  semantics for create, read/write, truncate, flush, rename, metadata, errors,
  enumeration, and close.
- Add one stable process-local identity and accurate system information.
  Process launch, enumeration, dynamic libraries, and native executable memory
  remain explicitly unsupported.

The focused subset initially disables PartitionAlloc and the allocator shim.
Those source graphs have their own missing Wasm platform selections and are not
needed to prove the M1 Base API behavior.

### Task runtime

The pinned `MessagePumpDefault` already waits through `WaitableEvent`, wakes on
cross-thread `ScheduleWork`, handles immediate and delayed work, and is selected
by `MessagePump::Create(DEFAULT)`. It has no file-descriptor dependency.

M1.2 therefore evaluates the generic pump first on the application pthread.
`//tools/wasm:m1_task_smoke` must prove delayed ordering, cross-thread wake,
nested loops, quit during sleep, bounded idle wake counts, and clean shutdown
while the browser heartbeat continues. A dedicated pump will be added only if
this behavioral gate exposes a real gap.

### Process-local shared memory

The current fallback in `platform_shared_memory_handle.h` names a POSIX
`FDPair` even though that type is not declared for Wasm. Wasm therefore gets a
separate process-local implementation; it does not reuse a Unix descriptor,
`mmap`, or a numeric value which could be mistaken for either.

#### Handle and identity

The platform handle is an opaque capability value containing a monotonically
allocated region ID, a generation, and rights. The scoped handle owns one
registry reference and is move-only. It never treats a storage address as the
transfer identity. The registry keeps the authoritative size, mode, and
128-bit `UnguessableToken` GUID; adoption checks all supplied metadata against
that record. A missing ID, stale generation, corrupted metadata, or rights
mismatch yields an invalid region or `TakeOrFail()` error instead of silently
creating an alias.

Writable ownership remains unique: it can be moved, converted to read-only, or
converted to unsafe, but not duplicated. Read-only and unsafe capabilities may
be duplicated when their typed Base APIs allow it. Conversion changes the
authoritative rights atomically and cannot promote a read-only capability back
to writable.

#### Storage and mapping lifetime

A locked, process-local registry owns each allocation independently of its
container. Storage is zero-initialized and aligned to
`SysInfo::VMAllocationGranularity()` (64 KiB for wasm32), which is stronger
than Base's public 32-byte minimum and lets partial mappings round-trip through
Base's align-down unmap path. The lock protects region creation, handle and
mapping reference counts, mode transitions, and lookup; callers synchronize
the bytes themselves through normal C++ atomics, locks, or other agreed
protocols.

Mapping validates the region ID, generation, current rights, offset, size, and
overflow before returning a span into the owning allocation. Every successful
map retains a mapping reference. Unmap decrements the matching
`{address, size}` count, so identical process-local mappings are supported.
Storage is freed only after both the final handle and final mapping are gone;
moving or destroying a handle therefore cannot invalidate an active mapping.
Zero-sized and out-of-range maps fail, and executable mappings are unsupported.

WebAssembly memory growth preserves intra-module pointer offsets, so C++
mappings remain valid. Growth can replace JavaScript's `ArrayBuffer` and typed
array views, however, so any later host bridge must reacquire a view after
growth; M1 exposes no persistent host view.

#### Protection boundary and limitations

Read-only enforcement is logical, not hardware-backed. The registry rejects a
writable map request made with read-only rights, and the public typed API
returns only `ReadOnlySharedMemoryMapping`. WebAssembly linear memory cannot
page-protect the same bytes from deliberately unsafe code already inside the
module, and M1 does not claim that guarantee. Existing writable mappings made
before demotion retain the lifetime and access promised by the pinned Base
API.

The focused M1 graph has tracing disabled. Native `mmap` normally provides a
distinct virtual address for each mapping, while this backend aliases the same
allocation; shared-memory usage tracking must therefore be explicitly omitted
for Wasm until it supports reference-counted duplicate addresses. The registry
still performs real ownership accounting and never fabricates distinct
mappings by copying storage.

### Mojo

This pin uses ipcz outside ChromeOS; enabling legacy Mojo would be the wrong
port. A local message pipe creates a pair of local ipcz routers, and attached
API objects move directly in a parcel without platform-handle serialization.

Compilation exposed native assumptions in `mojo::PlatformHandle`, platform
channels, and ipcz shared-buffer fallbacks. The implemented Wasm boundary adds
only the process-local shared-region capability needed by ipcz. Platform
channels and native C handle wrapping return explicit unsupported results.
Remote serialization is rejected.

The stable gate is:

```text
//tools/wasm:m1_mojo_smoke
```

It depends on `//mojo/core/embedder:embedder` and
`//mojo/public/c/system:system`, initialize one node, and use the C API to
create/map/write/attach/send/receive/extract/map/verify/close a shared buffer
through one local message pipe. It does not create an invitation, transport,
platform channel, or second node.

## Final architecture and source selection

M1 keeps one WebAssembly process. Emscripten `PROXY_TO_PTHREAD` moves each
test's application sequence off the host browser JavaScript main thread, and
Emscripten pthreads/Web Workers provide C++ and Rust workers. Wasm remains
separate from the global Linux and POSIX build flags.

The focused graph deliberately selects dedicated `*_wasm.cc` implementations
for clocks, randomness, paths, process/system behavior, threading,
synchronization, and process-local shared memory. POSIX-shaped file sources are
reused only where the actual Emscripten MEMFS descriptor semantics were tested;
host paths, process spawning, native priorities, file locking, and platform
channels are not inherited.

`//:gn_all` contains exactly these milestone executables:

```text
//wasm:hello_wasm
//tools/wasm:m1_base_smoke
//tools/wasm:m1_task_smoke
//tools/wasm:m1_rust_smoke
//tools/wasm:m1_rust_panic_negative
//tools/wasm:m1_shared_memory_smoke
//tools/wasm:m1_mojo_smoke
```

The M1.0 JSON inventory intentionally remains a historical snapshot of the
blocked pre-implementation graph. Final capability status is maintained in
[`porting_ledger.md`](porting_ledger.md).

## M1.1 Base platform result

The `//tools/wasm:m1_base_smoke` gate uses Chromium Base APIs and verifies:

- plausible wall time, monotonic high-resolution `TimeTicks`, elapsed time,
  and bounded thread sleep;
- cryptographic entropy on the application pthread and another worker;
- thread creation/join, stable IDs, best-effort diagnostic names, yielding,
  TLS isolation/destructors, locks, condition variables, manual/auto-reset
  events, timed waits, atomic handoff, and a bidirectional worker handshake;
- VFS current, temporary, and placeholder home paths;
- MEMFS create/open/read/write/seek/overwrite/append/truncate/flush/reopen,
  rename, metadata, nested directories, enumeration, errors, and cleanup;
- stable process-local identity and accurate Wasm page, heap, processor,
  architecture, and runtime-relative uptime facts.

Executable/module paths, file locking, non-current process handles, process
control and launch, output capture, native physical-memory/disk/CPU-model
queries, dynamic libraries, and executable memory are unavailable rather than
fake-success stubs. Thread names are diagnostic only, `ThreadTicks` is
unsupported, and MEMFS flush does not provide persistence.

The older roadmap also lists `base::Environment`, dedicated command-line
behavior, and symbolized Base stack traces. They are not part of the focused
M1 completion contract and have no M1 behavior test; the ledger keeps them
deferred instead of claiming support.

## M1.2 task runtime result

The pinned `MessagePumpDefault` passed the required application-pthread gate,
so M1 did not add a naming-only `MessagePumpWasm`. It blocks through the Wasm
`WaitableEvent`, wakes for cross-thread work, recomputes delayed deadlines,
supports nested `RunLoop` instances and quit-while-sleeping, and shuts down
without a polling loop.

`//tools/wasm:m1_task_smoke` proves immediate work, three ordered delayed
wakes, bidirectional application/worker posting, independent nested quit,
continued outer execution, sleeping quit wake, a bounded idle period, one
created/joined test worker, and no live worker at shutdown. The final observed
contract was 18 tasks, three delayed wakes, three wake requests, one delegate
idle wait, and nesting depth two. Native UI and I/O pump types remain
explicitly unsupported.

## M1.4 shared memory and Mojo result

The Base shared-memory implementation matches the design recorded above:
opaque capability identity, locked process-local registry, 64 KiB-aligned
storage, validated GUID/size/generation/rights metadata, independent handle
and mapping references, move-only writable ownership, duplicable read-only and
unsafe capabilities, duplicate-address unmap accounting, and explicit
wasm32/range/overflow checks.

`//tools/wasm:m1_shared_memory_smoke` verifies writable, read-only, and unsafe
regions; typed capability rejection; move/duplicate/conversion behavior;
partial and invalid mapping; stale and corrupted metadata; mapping lifetime
after handles close; and overlapping access from the application thread and
one worker. Read-only enforcement is logical at API/capability boundaries,
not hardware page protection inside linear memory.

Mojo uses the pinned ipcz core and exactly one in-process broker node.
`//tools/wasm:m1_mojo_smoke` creates a real Mojo message pipe, creates and maps
a shared buffer, writes deterministic bytes, attaches the handle to a message,
sends and receives it through local ipcz portals, extracts and maps it, verifies
and modifies shared bytes through the permitted unsafe capability, and closes
all handles cleanly. Invalid/stale capability metadata, oversized operations,
rights mismatch, remote transport, and driver allocation/map failure paths
reject. No invitation, platform channel, second node, Unix handle, or fake
descriptor is created.

## Test harness contract

The Node, browser, panic, and server runners share one manifest-driven harness.
Every run prints:

- the live Chromium port `HEAD`;
- `wasm-m0-primary-toolchain` and its peeled commit
  `831de29bfdf212c26f61ffbd828e5377732fb2bc`;
- manifest path, schema, and SHA-256
  `1cb3d79c97aec1f09084f6a57a1b5bbde0e746d3d4c9a18cb893224489a66c40`.

The runners enforce bounded timeouts, keep stdout/stderr separate, treat aborts
and nonzero exits as failures except for the isolated expected-panic case, and
return nonzero when validation fails. Browser cases additionally require a
sandboxed Chrome, cross-origin isolation, `SharedArrayBuffer`, canvas focus,
timer and animation-frame progress, no uncaught error, no Wasm abort, ordered
runtime sentinels, and the case's complete result contract. A browser failure
atomically saves structured diagnostics under
`out/wasm/diagnostics/<case>-browser-failure.json`, without saving the private
test URL or token.

## Known limitations and M2 recommendation

- This is a runtime foundation, not a browser: no V8, Blink, Content, Ozone,
  canvas browser presentation, WISP, OPFS, media, DevTools, extensions, PDF, or
  Chrome Views work has begun.
- The architecture is single-process and cannot provide the native sandbox,
  renderer process isolation, or Site Isolation.
- Shared-memory read-only rights are logical, not hardware-enforced.
- MEMFS is volatile; OPFS persistence remains a later milestone.
- Only one in-process ipcz node exists. Platform channels, invitations, remote
  serialization, and native handles are unsupported.
- PartitionAlloc, the Chromium Rust prelude, native Rust unit-test integration,
  symbolized Base stack traces, environment behavior, native UI/I/O pumps, and
  broader Content/Chrome Rust consumers remain deferred.
- The two-worker pool and fixed 2 GiB maximum are measured M0/M1 seed values,
  not final Chrome sizing.

The next task is M2's smallest standalone V8 experiment only: build the pinned
V8 with the outer wasm32 runtime and a 32-bit ARM simulator in jitless mode,
then execute a minimal but meaningful JavaScript acceptance slice. Do not load
Content, Blink, Ozone, or Chrome UI until that standalone V8 gate passes.
